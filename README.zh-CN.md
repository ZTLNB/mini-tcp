# mini-tcp

[English](README.md) | **简体中文**

用纯 Python 从零实现的一套 TCP/IP 协议栈。没有第三方依赖，没有用 `socket`
模块，没有 `asyncio`，没有 C 扩展。以太网、ARP、IPv4、ICMP、UDP、TCP 全部在这个
仓库里逐字节实现，而且能跑真实应用：示例程序会发起 HTTP 请求、提供 echo 服务，
并且在 35% 丢包的链路上把数据完整送达。

目的不是替代操作系统自带的协议栈。目的是让每一层都可见、可测、可解释——校验和
的进位折叠、序列号的回绕比较、11 个状态的迁移、拥塞窗口的增长、每一个定时器的
职责。如果你曾经想读懂 TCP 而不是靠信仰接受它，这个仓库就是为此写的。

## 实现范围

**链路层**

- 以太网 II 组帧：14 字节头部、发送时补齐到最短 60 字节
- 接收时**故意保留**填充字节。上层各有自己的长度字段，靠帧长推断有效载荷长度
  迟早会错——一个 60 字节的短 TCP 应答会被误当成带负载的数据
- 广播与组播识别
- 可插拔的 `Link` 抽象，两个实现：
  - `SimulatedLink`——进程内的虚拟链路，Windows 上也能跑，能按种子注入丢包、
    重复、乱序、损坏、延迟
  - `TunLink`——通过 `/dev/net/tun` 操作真实的 Linux TAP 设备

**ARP**

- 请求/应答，缓存**从任何 ARP 流量中学习**，而不只是应答。发出请求的一方已经
  告诉了你它住在哪，白扔掉这条信息是浪费
- 条目带超时，容量有上限，淘汰最接近过期的一条
- 未解析的目标地址会把待发数据包**暂存**，收到应答后自动补发，调用方看不到
  "还没解析好"这种中间状态

**IPv4**

- 头部解析与构造，带完整校验：版本、IHL、首部校验和
- 按 `total_length` 截断有效载荷，而不是按缓冲区长度——这条是短包不被以太网填充
  污染的关键
- 按任意 MTU 分片，偏移量以 8 字节为单位，DF/MF 标志正确
- 重组支持乱序、重叠、交错到达的分片；带超时和待重组集合数量上限，所以"只发首片"
  的洪泛无法耗尽内存
- 地址运算：前缀/掩码互转、同子网判断

**ICMP**

- echo 请求/应答，所以这套栈是可以被 ping 的

**UDP**

- 数据报，带 IPv4 伪首部校验和，包括"校验和为 0 表示未计算"这个约定

**TCP**

- 完整的 11 状态机：`CLOSED`、`LISTEN`、`SYN-SENT`、`SYN-RECEIVED`、
  `ESTABLISHED`、`FIN-WAIT-1/2`、`CLOSE-WAIT`、`CLOSING`、`LAST-ACK`、`TIME-WAIT`
- 三次握手、同时打开、被动打开、四次挥手、`TIME-WAIT` 2×MSL 超时
- 选项解析与协商：MSS、窗口扩大因子、SACK-permitted、时间戳、NOP/EOL 填充
- **防回绕的序列号运算**（RFC 1982），并且对 2³¹ 这个"未定义"情形如实报告，
  而不是悄悄选一个方向然后一半概率答错
- **RTT 估计**（RFC 6298）：SRTT/RTTVAR、`RTO = SRTT + 4×RTTVAR`、上下限钳制、
  指数退避
- **Karn 算法**：重传过的报文段不提供 RTT 采样，因为它的确认是有歧义的
- **Reno 拥塞控制**：慢启动、拥塞避免、三个重复 ACK 触发快重传、快速恢复、
  超时塌缩
- **流量控制**：通告窗口、窗口扩大、接收缓冲是**硬上限**，无论对端发什么
- **延迟确认**、**零窗口 persist 定时器**、**退避后能恢复的重传定时器**
- 重传、重复检测、重叠裁剪、字节流级别的乱序重组
- 发送侧与接收侧的 RST 处理

**周边**

- `pcap` 写出，抓包文件能直接用 Wireshark 打开
- 报文摘要器，输出 tcpdump 风格的一行描述；**校验和错的包也照样打印**——做协议
  分析的时候，坏包恰恰是最值得看的东西

## 快速开始

不需要安装，没有依赖。Python 3.10 及以上。

```bash
git clone https://github.com/ZTLNB/mini-tcp.git
cd mini-tcp
```

### 看一次完整的 TCP 会话，逐包展开

```bash
python examples/loopback_demo.py
```

它会构造两个完整的协议栈，用虚拟链路连起来，做一次 HTTP 交互，并把每个经过的
数据包打印出来。最后校验载荷完整性并输出连接统计。

### 起一个真实连接并压它

```bash
python examples/echo_server.py                    # 进程内，无丢包
python examples/echo_server.py --loss 0.35        # 丢掉 35% 的数据包
python examples/echo_server.py --duplicate 0.1 --reorder 0.05
```

### 直接用套接字 API

```python
from minitcp import socket, AF_INET, SOCK_STREAM
from minitcp.link import SimulatedLink, VirtualWire
from minitcp.stack import Stack

wire = VirtualWire()
client_stack = Stack(SimulatedLink(b"\x02\x00\x00\x00\x00\x01", wire), "10.0.0.1", 24)
server_stack = Stack(SimulatedLink(b"\x02\x00\x00\x00\x00\x02", wire), "10.0.0.2", 24)
client_stack.start()
server_stack.start()

server = socket(server_stack, AF_INET, SOCK_STREAM)
server.bind(("0.0.0.0", 8080))
server.listen()

conn = socket(client_stack, AF_INET, SOCK_STREAM)
conn.connect(("10.0.0.2", 8080))
conn.sendall(b"hello")
```

### 走真实网卡（仅 Linux）

`TunLink` 需要 `CAP_NET_ADMIN`：

```bash
sudo python examples/http_get.py --iface tap0 --host 93.184.216.34 --pcap capture.pcap
```

然后用 Wireshark 打开 `capture.pcap`，和协议栈自己认为发生的事情对照着看。

## 测试

```bash
python -m unittest discover -s tests -v
```

279 个用例，约 30 秒，**不用第三方测试框架**——就是标准库 `unittest`，这样"零依赖"
这个说法才贯彻到底。

| 文件 | 覆盖内容 |
| --- | --- |
| `tests/test_units.py` | 217 个用例，覆盖每个编解码器和算法。期望值取自 RFC 和公开的演算示例，而不是取自代码本身 |
| `tests/test_loopback.py` | 27 个用例，让两个真实的 `TCPConnection` 通过可编程链路对话，时钟由测试控制——所以时序永远不会变成竞态 |
| `tests/test_stack.py` | 10 个用例，走套接字 API 和两个完整协议栈，包括在丢包 10% 的链路上传 20 kB |
| `tests/test_fuzz.py` | 25 个用例，把随机字节、有效报文的每一个截断前缀、逐位翻转的变异喂给全部六个解析器和一条活跃连接 |

有三点值得单独说明：

- **校验和测试不是自证的。** 它断言 RFC 1071 的演算示例（`00 01 f2 03 f4 f5 f6 f7`
  → `0x220d`）和 IPv4 首部的经典向量（`0xb861`），然后验证 500 次单位翻转
  **全部**被捕获。一个只断言"代码输出什么"的测试比没有测试更糟。
- **丢包测试是确定性的。** `FaultProfile` 接受种子，所以失败能精确复现，而不是
  每四十次跑挂一次。
- **模糊测试断言的是异常*类型*，不只是"没崩"。** 解析器只允许用 `ValueError`
  拒绝坏输入。如果它抛别的，调用方无法把"报文坏了"和"我这儿有 bug"区分开，
  错误处理就有洞。

## 设计取舍

### 为什么链路层是可插拔的

最初的打算是直接写 TAP 设备，因为那才是"真实"的。问题是 `fcntl` 和
`/dev/net/tun` 都是 Linux 专有，在 Windows 上连 `import` 都会失败，测试也就无从
谈起——而协议栈里 90% 的复杂度和平台毫无关系。

所以把链路层抽成 `Link` 抽象：`SimulatedLink` 在进程内直接传递帧，`TunLink` 操作
真实设备，两个实现都只是"收发以太网帧"。带来的好处远超预期：

- 整个测试套件在任何平台上都能跑，而且不需要 root
- 故障注入变成可能。真实网卡不会按你要的比例丢包，虚拟链路可以
- 时钟可以注入。`Loopback` 测试用假时钟，所以"RTO 到期后重传"这类断言是
  确定性的，不靠 `sleep` 和运气

代价是模拟链路复现的是**行为**而不是**性能**——它不模拟带宽和排队。

### 为什么时钟要可注入

这一条单独说，因为它直接决定了测试能不能写。协议栈里几乎每个重要行为都和
时间有关：重传、退避、延迟确认、`TIME-WAIT` 过期。如果这些都读
`time.monotonic()`，测试就只能 `sleep`，然后变得又慢又飘。

`TCPConnection` 的构造函数接受一个 `clock` 可调用对象。生产代码传
`time.monotonic`，测试传一个能手动推进的假时钟。于是一个涉及四次退避重传的
场景能在**微秒**内跑完，而且每次都走同一条路径。

### 为什么零窗口不能靠"试探"解决

对端窗口关死的时候，发送方**不能**继续推进 `snd_nxt` 发新数据。这一点很反直觉，
因为"反正对端有缓冲区，先发过去"看起来很合理。

问题在于：窗口关死意味着对端明确告诉你它没地方放了。你发过去的字节，对端有权
直接**拒绝**而不是缓存。一旦被拒绝，你就消耗掉了序列号，却在 `snd_una` 位置留下
一个空洞——这个洞只有超时重传才能补上。

更糟的情况是：重新开窗的那个 ACK 如果在路上丢了，发送方手里有数据、接收方手里
有空间，**双方都没有理由再开口说话**。连接就这么死锁了，没有任何错误。

所以这里的做法是：窗口关死时 `_flush` 什么都不发，改为启动 **persist 定时器**；
到期后从 `snd_una` 发一个探询，退避从 0.5 秒爬到 60 秒上限，但**永不放弃**。
同时，窗口一旦重新打开，立刻从在途队列头部重发，而不是干等 RTO。

### 为什么窗口更新会伪装成重复 ACK

重新打开窗口的那个 ACK，其确认号**不可能前进**——因为窗口关着的时候，对端根本
没接受任何新数据。所以从 ACK 号上看，它和重复 ACK 一模一样，唯一的区别在窗口
字段。

如果因为"确认号没前进"就整个丢弃这个报文段，结果就是上面说的死锁。这里的做法
是：**每个报文段携带的窗口字段都是权威的**，无论确认号是否前进；同时这个重复
ACK 依然计入拥塞控制的重复计数——它确实是一个重复 ACK，两件事互不冲突。

### 为什么流量控制必须自己强制执行

通告窗口告诉对端"我这儿还有多少空间"。守规矩的对端会尊重它。不守规矩的（或者
有 bug 的）不会，而接收缓冲区原本会**无限增长**——这恰恰是流量控制存在的意义。

`ReceiveQueue._accept` 现在会裁掉装不下的部分。被裁掉的尾部从未被确认过，所以
对端会重传，数据不会丢；而缓冲区无论收到什么都是硬上限。

## 踩过的坑

这一节是真正花时间的地方。每个 bug 都附了根因和修法——有些症状看起来和根因
毫无关系。

### 1. `snd_nxt` 回退会让发送路径永久停滞

**症状**：链路有丢包时，传输完全卡死。调试输出显示 `una=...191 nxt=...190`——
`nxt` 跑到 `una` 后面去了，而重传计数从 1 一路涨到 15。

**根因**：重传时把 `snd_nxt` 回退到被重传的序列号，看起来"整洁"，其实是个陷阱。
那个报文段被确认后，`snd_una` 越过了 `snd_nxt`，于是"在途字节数"算出来是负数，
`_flush` 里的 `in_flight < window` 永远成立也永远不成立（取决于符号），发送路径
就再也不动了。更隐蔽的是，重传路径每次还会往重传队列里塞一份新的副本，
同一个序列号出现两次。

**修法**：`SendQueue.acknowledge` 里把 `nxt` 单向钳制向前
（`if seq_lt(self.nxt, ack): self.nxt = ack`），重传路径**不再**回退 `nxt`。

### 2. 一个 `Edit` 只改了调用点，没改函数定义

**症状**：`TypeError: TCPConnection._transmit() got an unexpected keyword
argument 'track'`，但**栈里什么都看不到**——重传定时器只是不再重新装载，
表现为"偶尔卡一下"。

**根因**：我给两个调用点加了 `track=` 参数，但函数定义那一行没改到。异常被
协议栈里的 `except Exception` 吞掉了。

**教训**：诊断方式是临时给 `_on_retransmit_timeout` 打猴子补丁打印 traceback，
然后用 `grep` 确认只有调用点带 `track=` 而 `def _transmit(` 那一行没有。这件事
直接促成了后面两处改动：让 `handle_frame` 只捕获 `ValueError`（坏包）而让真正的
bug 冒出来；读取线程遇到意外异常时单独计数并**保留错误信息**——一个静默死掉的
读取线程看起来和"网络很安静"一模一样，是最难查的那种故障。

### 3. FIN 跨过序列号空洞会丢数据

**症状**：15% 丢包时，第二条消息回显为 0 字节。

**根因**：`_handle_fin` 无条件执行 `recv_queue.nxt = seq_add(fin_seq, 1)`。当
FIN 的序列号落在 `rcv_nxt` **之后**（中间还有没到达的数据），这一句直接把
`rcv_nxt` 跳过空洞，那批数据被永久丢弃。

**修法**：只有在 `fin_seq == rcv_nxt` 时才推进，否则回一个 ACK 继续等空洞填上。

### 4. `peer_closed` 把 FIN-WAIT-2 也算进去了

**症状**：客户端关掉自己的发送方向后，立刻认为整个流已经结束，在响应到达之前
就收摊了。

**根因**：`FIN-WAIT-2` 的含义是**我方**已关闭，对端仍然可以继续发送。把它当成
"对端也关了"是错的。

**修法**：改成只有 `CLOSE-WAIT`、`CLOSING`、`LAST-ACK`、`TIME-WAIT` 才算。

### 5. RTO 退避之后再也回不来

**症状**：时间戳日志显示一个 408 字节的报文段在 t=7.4s 已被确认，之后**又被
重传**了一次，此时 `rto=16.00`。

**根因**：这个报文段被重传过，所以 Karn 算法正确地抑制了它的 RTT 采样。但抑制
采样的同时，**指数退避也留在了原地**——没人把它撤掉。剩下的那个 FIN 只能干等
一个 8 秒的定时器。一条已经证明自己活着的链路，却在无谓地等 8 秒。

**修法**：新增 `RTOEstimator.recompute()`，在 `_process_ack` 里当"没有任何可用
采样"时调用它，把退避撤掉。确认号在前进，就说明路是通的。

### 6. 重复 ACK 上的窗口更新被整个丢弃（零窗口死锁）

**症状**：接收方的窗口早就恢复到 65535 了，发送方却还认为窗口是 0，双方死锁。
诊断输出：

```
client: peer_window=0   una=286462224 nxt=286463684   ← 还有 1460 字节发不出去
server: nxt=286462224   avail=0  window=65535          ← 窗口早就打开了
```

**根因**：`_process_ack` 在"确认号不前进"时直接 `return`，顺手把窗口字段也扔了。
而"窗口从 0 恢复"这件事**必然**以重复 ACK 的形式到达——见上面"为什么窗口更新会
伪装成重复 ACK"。

**修法**：见对应章节。这一条是整轮调试里最隐蔽的，因为两边的状态各自看都完全
正常，只有放在一起才看得出矛盾。

### 7. 用 `max(min(cwnd, peer_window), mss)` 当窗口，零窗口时仍会推进 `snd_nxt`

**症状**：4096 字节的小窗口下传 20000 字节，传到 19304 就停了，`retx=0`——
没有任何重传触发器。乱序队列里孤零零躺着 412 字节，`snd_una` 位置有个 696 字节
的空洞。

**根因**：`effective_window` 里的 `max(..., mss)` 本意是避免"愚蠢窗口综合征"，
但用在**零窗口**上就变成了"允许一个 MSS 的新数据上路"。`_flush` 于是把 696 字节
推进了一个关闭的窗口，对端拒收一部分、暂存一部分，空洞就此产生。而发送方已经
发完了所有数据（`unsent=0`），重传队列里那两段又没被任何机制触发重传。

**修法**：`_flush` 在 `peer_window <= 0` 时直接返回并启动 persist 定时器，
一个新字节都不推进。

### 8. 接收缓冲区没有上限

`ReceiveQueue` 的模块文档写着"缓冲区满了，通告窗口会缩到零，对端就会停"——
但 `_accept` 从来没检查过容量。对端如果不守规矩，缓冲区就是无界的。

**修法**：`_accept` 按剩余空间裁剪，`_ooo` 的暂存也按剩余窗口而不是自身容量
设限，这样 `available + held` 永远不会超过容量。

### 9. 解析截断数据时抛 `struct.error` 而不是 `ValueError`

`Reader.u32()` 在数据不够时抛的是 `struct.error`，而 `Reader.raw()` 抛
`ValueError`。解析不可信网络数据时，调用方需要一个统一的异常类型来区分"报文
损坏"和"代码有 bug"。

**修法**：`Reader` 的每个访问器都先检查长度，统一抛 `ValueError`；`Writer` 的
越界值也从 `struct.error` 改成 `ValueError`，两边契约一致。

### 10. 属性还是方法，前后不一致

`IPv4Packet.is_fragmented` 是属性，`TCPSegment.is_syn` 是属性，而
`EthernetFrame.is_broadcast` 是方法。同一个概念三种写法，调用方必须去查。

**修法**：统一成属性（只有一处外部调用点，改动很便宜）。写单元测试时正是这一点
先暴露出来的——`assertFalse(frame.is_broadcast)` 对一个方法永远失败，因为绑定
方法对象本身是真值。

## 已知限制

如实列出。这些是有意的范围边界，不是疏漏。

- **没有实现 SACK。** 协商了 SACK-permitted，也解析了这个选项，但不据此做选择性
  重传：发生丢包时从 `snd_una` 重传，而不是只补缺失区间。
- **没有时间戳（RFC 7323）RTTM。** 选项能解析，RTT 靠报文段发送时间测量——这也
  是真实协议栈在关闭时间戳时的做法。
- **拥塞控制只有 Reno。** 没有 CUBIC、没有 BBR，ECN 只解析标志位不做响应。
- **`TunLink` 仅限 Linux。** 依赖 `/dev/net/tun` 和 `fcntl`。这个模块在 Windows
  上能安全导入，只有真的去打开设备时才会报错——整个测试套件因此能在任何平台跑。
- **只有 IPv4。** 没有 IPv6、没有 IP 选项、没有路由协议。
- **模拟链路不是网络。** `SimulatedLink` 在同一个进程里直接传递帧，它复现的是
  有损链路的**行为**，不是它的吞吐特性。
